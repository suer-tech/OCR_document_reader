# Тестирование OCR

## Определи объём проверки

1. Начни с ожидаемого результата из задачи, API-контракта и профиля в `OCR-document-parser/src/ocr_platform/config/pipelines/profiles/`. Найди реальные входы в изменённый код и его вызывающие участки. Существующий код и тесты показывают текущее поведение. При конфликте контрактов выясни, какое поведение подтверждено, и отмечай открытые вопросы.
2. Перечисли **все затронутые поля и профили**, разделив поля на обязательные, необязательные и условно обязательные. Для общей функции проверь каждое затронутое поле в подходящей для него форме. Объединяй одинаковые сценарии параметризацией, сохраняя отдельные тесты для различающихся контрактов. Источник списка полей — профиль или схема. Ожидаемые значения, статусы и число попыток фиксируй по контракту.
3. Для каждой изменённой развилки выпиши применимые исходы и наблюдаемый результат. Учитывай успешный результат, допустимое отсутствие, ошибку или отклонённое значение, восстановление при повторе и исчерпание попыток. Если правило влияет на побочные эффекты, учти повторную доставку, изменения в БД, очередь и ручную проверку. Для условных полей проверь оба состояния условия. Если меняется чтение сохранённых результатов, добавь случай с историческими данными. Цель — покрыть исходы затронутой логики. Глобальный процент служит для диагностики.

### Проверка одного профиля

- Используй точный `profile_id` и текущий YAML. У решений суда это `court_decision_ru`, у РТК — `rtk`, у РТК-2 — `rtk2`, у РТК-3 — `rtk3`. Для паспорта выбери `passport_main` или `passport_registration` по проверяемой странице.
- Основной сценарий запускай через действующий режим и реальные точки входа профиля. Старый режим включай в отдельном тесте, когда проверяешь поддерживаемую совместимость или чтение исторического результата.
- Для задачи по одному профилю передавай явные селекторы его тестов. В общем файле выбирай конкретный тест или параметр профиля по node ID. Например, для РТК-3 выбирай файлы `tests/services/test_rtk3_*.py` и при необходимости сценарий API для РТК-3. Файлы `test_rtk2_*.py` относятся к РТК-2. При правке общего кода добавь сценарии только тех профилей, поведение которых меняется.

## Напиши тесты по контракту

- Для дефекта воспроизведи ошибку тестом и проверь причину его падения, затем исправь код и повтори тот же тест. Для нового поведения держи тесты в той же правке, что и реализацию.
- Проверяй наблюдаемый эффект. Для повторов это запрос именно нужных полей, число вызовов, сохранность уже извлечённых значений и итоговый статус. Для идемпотентности — прежние ID, один файл, одна запись и одно задание. Проверка вызова заглушки дополняет проверку результата через API, воркер или БД.
- **Пример масштаба.** При правке общего правила обработки ошибки распознавания составь список по каждому затронутому полю. Текстовые поля `creditor` и `grounds`, денежное `claims_amount` и необязательный `creditor_inn` могут получать разные формы отказа. Для `case_number` отдельно установи, затронут ли путь регулярного извлечения или общей валидации. Проверь каждое применимое поле по его контракту. Для повторов проверь также сохранение корректных значений, включая `0` и `false` там, где контракт их допускает.
- Используй синтетические данные, тестовую SQLite и заглушки на границах внешних моделей, HTTP и брокера. Для БД используй `isolated_db`, если она есть в текущей версии `tests/conftest.py`. Тестируй собственный процессор, валидатор или API до точки подмены. Рабочие API, БД, очередь и реальные модели в тестах не используются.

## Запусти и проверь

Из корня репозитория используй Python с установленными зависимостями `OCR-document-parser[dev]`. [Офлайн-запуск](scripts/run_tests.py) принимает пути относительно `OCR-document-parser` и селекторы pytest. Он создаёт временный каталог, использует тестовую SQLite и блокирует внешние DNS-запросы и соединения из процесса Python.
Для другого worktree укажи `--project-dir` с путём к его `OCR-document-parser`. Селекторы тестов указывай относительно этого каталога.

```text
python .agents/skills/ocr-testing/scripts/run_tests.py tests/test_queue_budget_and_lock.py
python .agents/skills/ocr-testing/scripts/run_tests.py --coverage-dir runs/ocr-test-coverage tests
python -m ruff check --config OCR-document-parser/pyproject.toml OCR-document-parser/src/ocr_platform OCR-document-parser/tests
```

Команда для набора РТК-3 из корня рабочей копии в PowerShell.

```powershell
$rtk3Tests = Get-ChildItem OCR-document-parser/tests/services -Filter 'test_rtk3_*.py' -File | ForEach-Object { "tests/services/$($_.Name)" }
python .agents/skills/ocr-testing/scripts/run_tests.py --coverage-dir runs/rtk3-coverage --report-prefix rtk3_ @rtk3Tests
```

Запусти сначала точечные тесты, затем набор затронутого профиля или профилей. Полный набор запускай для проверки всего сервиса, например при правке общих механизмов, затрагивающей все профили, или по отдельной задаче на полный регресс. Вызов скрипта без селекторов также запускает полный набор. При сверке с CI используй workflow, действующий в проверяемой ветке. В отчёте покрытия найди конкретные пропущенные переходы изменённых функций и сопоставь их со списком сценариев. Если переход остаётся непроверенным, укажи какой и почему. В итогах зафиксируй проверенные поля и ветви, результаты pytest и Ruff и путь к артефакту покрытия. Рост покрытия сам по себе показывает больше выполненного кода.

## Покажи результат наглядно

Для итогового прогона укажи `--coverage-dir`. Скрипт создаст интерактивный `dashboard.html`, инфографику `infographic.png` и исходный отчёт `html/index.html` с данными в `coverage.json`. Ссылка на дашборд и инфографика идут в ответ пользователю вместе с результатом тестов.

`--report-prefix` задаёт срез файлов для сводных показателей и начального списка в дашборде. Состав запускаемых тестов по-прежнему задаётся селекторами. При проверке одного профиля поясни показатели его файлов, затем покажи конкретные пропуски в изменённой логике. Строки и переходы, до которых тесты не дошли, учитываются в покрытии. Падения тестов показываются отдельно. Точность извлечения полей оценивается на размеченных документах.

# Извлечение решения суда: регулярки, JEV, адресный LLM

## Цель и статус

Целевая схема согласована 20 октября 2026 года: сначала документные поля
извлекаются регулярными правилами, затем проверяются `typesafe/jev-1.14` через
RouterAI, и только неподтверждённые поля запрашиваются у LLM. Новая схема включена
в локальном профиле `court_decision_ru`; сервер не обновлялся.

Состояние для GitHub на20.10.2026:27 полей, короткие индивидуальные вопросы,
порог JEV0,60, только настроенный Claude через RouterAI для извлечения
неподтверждённых полей. Повтор LLM не меняет модель, после LLM JEV не вызывается.
Последняя локальная проверка:1612 тестов прошли с прежним исключением старого
`tests/services/test_glm_ocr_service.py`. Выборка10 исторических решений
до11.09.2026 ещё не получена из-за отсутствия подтверждённого доступа к серверу;
нового сетевого замера на этих10 нет. Публикация ветки не является выкладкой.

20 отдельных модулей полей завершены субагентами; основной агент объединил их
с семью существующими полями в реестр 27 полей. Реализованы нативный API JEV,
адресный типизированный LLM fallback и точка подключения через
`extraction_mode: regex_jev`. Все 355 текстов проверяются локально без HTTP;
сетевые проверки ограничены выбранными документами. Полный корпус через
RouterAI не отправляется. Промежуточный замер на двух документах: 58,57 секунды,
2 JEV + 2 LLM против 76,34 секунды и 12 LLM прежней схемы. Это не оценка
скорости всего корпуса; окончательный протокол хранится в analysis.

Для возврата к прежнему маршруту удалите `extraction_mode: regex_jev` из профиля.
Параметры `extraction_method` отдельных полей сохранены для прежнего маршрута;
при `regex_jev` ими не обходится обязательная проверка JEV.

## Контракт

### Порог0,60 и десять более ранних решений, 20.10.2026

По прямому указанию пользователя порог принятия JEV в профиле суда снижается
с0,95 до0,60. Пользователь разрешил взять на сервере10 судебных решений,
обработанных раньше самого раннего периода исходного датасета с ручной разметкой,
и проверить их действующим маршрутом с короткими вопросами и одним Claude.
Выбор фиксируется до получения новых ответов, пересечение с355 исходными PDF
исключается по SHA-256. Даты создания документов и обработки проверяются отдельно;
исторические машинные значения не выдаются за ручную разметку.

Полный корпус355 в сеть не отправляется. Сервер используется для чтения
исторических входов; это разрешение не является командой развернуть новую версию.

### Только настроенный Claude, без смены модели, 20.10.2026

Пользователь уточнил: извлечение выполняется Claude через RouterAI, переходов
на другие LLM при ошибках нет. `openai/gpt-oss-120b` был указан в исходном
профиле суда ещё в HEAD до сегодняшней работы; сохранение этой цепочки в новом
маршруте было ошибкой. Резервная модель удаляется из профиля, адресный сервис
передаёт шлюзу только основную модель даже при старом `fallback_models`.
Повтор невалидного ответа может использовать только ту же настроенную модель.
После исчерпания попыток поле получает `validation_issue` для ручной проверки.

Классификация типа документа также переводится с прежней цепочки GPT-OSS / Claude
через OpenRouter на один Claude через RouterAI. При отсутствии явной конфигурации
используется одна модель из Settings; прежние списки резервных моделей не читаются.
OCR и проверка JEV остаются отдельными согласованными этапами.

Исторический прогон трёх решений не переписывается: в А33-10373/2026 действительно
сработал GPT-OSS после неразобранного JSON Claude. Его нельзя представлять как
результат только Claude; остальные два решения обработаны Claude без смены модели.

Проверки исправления:9 новых тестовых случаев,55 выборочных проверок и1609
тестов полного набора прошли с прежним исключением старого GLM-модуля.
Проверены неизменность модели при неразобранном JSON и невалидном поле,
ручная проверка после исчерпания попыток, отказ от старых резервных списков,
настройки классификатора и наличие только ключа RouterAI. Ruff и diff check
чистые. Сетевых вызовов для исправления не выполнялось.

### Короткие индивидуальные вопросы JEV, 20.10.2026

По прямой команде пользователя вопросы для всех 27 полей переводятся в формат
«Соответствует ли предложенное значение конкретному полю текущего дела по
тексту документа?». Для ФИО достаточно указать именительный падеж; таблицы
склонений, окончания и примеры морфологических преобразований не добавляются.
Длинная общая инструкция и полные `FIELD_RULES` к каждому вопросу не приписываются.
Подробные правила адресного LLM остаются прежними.

Для отсутствия значения задаётся отдельный короткий вопрос по смыслу поля.
У булевых значений вопрос проверяет именно предложенное true/false. Согласованные
подстановки дат и границы частей акта сохраняются в своих вопросах. Полный
документ остаётся источником проверки, кандидаты не считаются доказательством.
Меняются только формулировки JEV: порог, регулярки, зависимости и маршрут
LLM не меняются. Локальные проверки вопросов не доказывают улучшение живой JEV;
сетевые замеры требуют отдельного малого выбранного набора.

Реализация: `services/court_jev_questions.py`; полный список сформированных
вопросов — [COURT_JEV_QUESTIONS.md](COURT_JEV_QUESTIONS.md).
На трёх сохранённых входах проверены81 вопрос и неизменность regex-значений
с исходными диапазонами. Суммарная длина инструкций уменьшилась с88008
до18871 символа (−78,6%); это длина строк, не токены и не замер скорости.
Прошли1600 локальных тестов с прежним исключением старого
`test_glm_ocr_service.py`; Ruff чистый. Сетевых запросов для этой правки не было.

### Синтетическая проверка ФИО, Telegram157

Зафиксирован набор355 новых ФИО:255 для поиска ошибок и100 отложенных,
по10 сценариев на ФИО. Фамилии и их формы отсутствуют в355 исходных документах;
ожидаемые падежи заданы вручную без вызова проверяемого нормализатора.
Есть именительный, родительный, дательный, винительный, творительный падежи,
сверка повторов, переносы строк, другие роли и конфликты.
Первый прогон выявил неполную обработку двойных фамилий и отдельных падежей
имён. Доработка применяется к классам окончаний и общим словарным исключениям;
неоднозначное обратное склонение не превращается в доказанное написание.
Отложенная часть оценивается после исправлений, без предварительного запуска.

Каждый кандидат хранит значение, буквальный исходный фрагмент и его позиции.
Недоступные в документе данные не восстанавливаются по разметке датасета.
Найденное регуляркой значение автоматически верным не считается.

Один запрос JEV содержит полный OCR-текст, кандидатов и независимый вопрос для
каждого поля с его правилами. Используется нативный `/api/v1/decisions`, тип
вопроса `noul`; ответ — вероятность «да» от 0 до 1. Это не гарантированная
точность и не булево значение. Текущий порог0,60 задан конфигурацией по команде
пользователя20.10.2026. Вопрос содержит
конкретное значение кандидата (`question_style: concrete`). На четырёх выбранных
документах проверены 107 заведомо неверных предложений, включая ложное отсутствие:
ни одно не превысило прежний порог0,95. Это ограниченная историческая проверка,
а не гарантия точности при новом пороге0,60.

Невалидный ответ, пропуск вопроса, недостаточный порог или ошибка API ведут
к извлечению соответствующего поля существующим LLM-механизмом. Подтверждённое
поле в LLM повторно не передаётся. Полученное LLM значение повторно в JEV не
отправляется. Отсутствие regex-кандидата тоже требует fallback, если нет
отдельного подтверждения отсутствия. Для необязательного поля с обычным отказом
`not_found` и аналогичными причинами JEV отдельно проверяет отсутствие значения
по всему документу. Конфликт, некорректная дата/номер, неполный адрес и другие
ошибки не превращаются в подтверждаемое отсутствие. Нельзя автоматически
подтвердить `null` для обязательного поля. Если LLM не вернула обязательное
значение либо ответ не прошёл проверки после повторов, сохраняется
`validation_issue`; любой такой сбой поля новой схемы требует ручной проверки,
даже при высоком общем балле качества.

HTTP-вызовы остаются в `services/llm_gateway.py`, общая логика — в `services`,
точка подключения — `document_intel_service.simple_extract_fields`. Сохраняются
логи с document_id/pipeline_run_id, метрики попыток/времени/токенов и MLflow.

## Проверки

### Уточнение срока отчёта, Telegram145 от 20.10.2026

Пользователь указал считать `early_report_deadline` как `next_session_date`
минус ровно десять календарных дней при требовании заранее подать отчёт,
включая «заблаговременно», «за 3 дня» и «за 5 дней». Следующая дата берётся
по действующему правилу: явное рассмотрение, иначе окончание процедуры.
Без этой даты расчёт невозможен. Подтверждение срока зависит от JEV-проверки
следующей даты, а при её подстановке — транзитивно от окончания процедуры.
JEV и LLM используют одно правило; повторного JEV после LLM нет.
Приоритет явно указанной даты подачи и перенос выходных остаются вопросами
оператору. Предварительная сверка355: кандидатов113→115, совпадений95→100,
семь изменённых документов, ни одного утраченного прежнего совпадения.

Сравнение с ручной разметкой отдельно считает непустые совпадения, пустые поля,
отсутствующий ключ и каждое утраченное совпадение. Неоднозначные или внешние
операторские значения не превращаются в специальные правила для отдельных ID.
Замеряются количество запросов LLM/JEV и длительность; ускорение до замера не
объявляется.

## Доработка обязательных полей на 355 документах

Повторная цель 20 октября 2026 года покрывает все 13 обязательных полей.
На неизменном OCR-корпусе полный комплект regex-кандидатов найден в 128 документах
вместо 73, на фиксированной случайной десятке — в пяти вместо трёх. Это полнота
кандидатов, не подтверждённая точность и не доля документов без LLM после JEV.
Один из 128 комплектов имеет явную пометку неоднозначной формы фамилии.

Адрес регистрации: 259 → 298 кандидатов; дата резолютивной части: 122 → 174;
судья: 352 → 354. Прежние непустые совпадения с оператором по обязательным полям
сохранены. Небезопасные предложения отдельно отозваны при двух разных адресах,
конфликте текущих должников или заведомо косвенной фамилии без доказанной
именительной формы. Значения 14 необязательных полей не изменились.

Дата самостоятельной резолютивной части теперь допустима при явном заголовке
и близкой согласованной дате шапки. Нельзя подставлять дату полного решения
в документе, где отдельной даты резолютивной части нет. В 140 документах это
единственная незаполненная обязательная позиция; обязательность профиля сохранена.

Персональные поля исключают точный блок постороннего исторического заявления
только при согласованных текущих шапке и признании банкротом. Предшествующая
дата принятия заявления не исключается. Ребёнок/супруг не наследуют роль должника.
Все цитаты и позиции относятся к неизменённому входному тексту.

Проверки: 1493 теста с исключением двух заранее известных старых GLM-тестов,
7696 буквальных диапазонов и 1065 SHA-256 исходных файлов. Сетевых запросов нет.
Полные результаты, ограничения и изменённые документы:
[итог обязательных полей](../../analysis/pau-intro-decisions-2026-10-20/required-regex-improvements/REPORT.md).
Правила адреса отдельно: [COURT_REGEX_REGISTRATION_ADDRESS.md](COURT_REGEX_REGISTRATION_ADDRESS.md).

### ФИО должника: возвращено в регулярки → JEV → LLM, 20.10.2026

Последующая команда Telegram141 / update490870872 отменяет постоянный прямой
LLM для этого поля. Активный режим `regex_jev_mode: regex_jev`: источниковый
кандидат регулярки отправляется в JEV; при отказе либо отсутствии кандидата
только ФИО извлекается LLM. Результат LLM повторно JEV не проверяется.
Существующий regex поддерживает роль должника, падежную нормализацию и
источниковые цитаты; исходные конфликты/неоднозначные фамилии сохраняются.

Прежняя NLP-модель найдена в
`NLP-entity-extractor/src/inference/transformer.py`:
`Gherman/bert-base-NER-Russian`, компоненты LAST_NAME/FIRST_NAME/MIDDLE_NAME;
`postprocess.py` использует pymorphy3 для именительного падежа. Её наличие
в исходниках не означает наличие загруженных весов в работающем процессе.
Текущий маршрут использует готовый regex-кандидат; автоматического скачивания
и включения старой модели не выполняет.

#### История временного прямого LLM (заменён командой Telegram141)

По Telegram сообщению 77 (update 490870859) `debtor_full_name` получает
`regex_jev_mode: direct_llm` в конфигурации поля. Оно сразу отправляется
отдельным запросом в существующий типизированный LLM-экстрактор, параллельно
обычной ветке остальных полей. В JEV это поле не передаётся; результат LLM
повторно не проверяется JEV. Проверки формата, цитаты и обязательности остаются.
Исходник regex ФИО сохраняется для определения личности в других правилах,
но его значение не является предложением финального поля ФИО должника.
ФИО судьи остаётся в regex → JEV: 354/355 совпадений, оставшийся текст обрезан.

Прямой маршрут помечается `extraction_route=direct_llm`; значение сохраняет
совместимый `source=court_llm_fallback`, поскольку используется тот же
типизированный сервис с теми же проверками. Метрики: `direct_llm` по полю,
длительность `direct_llm` и `total_with_direct_llm`; лог содержит document_id
и pipeline_run_id. Тест с двумя событиями проверяет параллельный запуск,
отсутствие ФИО в вопросах/состоянии JEV и защиту остальных принятых полей
от перезаписи. Пустой ответ обязательного поля ведёт на ручную проверку.
Все 1528 тестов прошли без двух известных старых GLM-тестов; Ruff и diff check
чисты. Лог: `analysis/pau-intro-decisions-2026-10-20/direct-debtor-name-llm-tests.log`.
Живых сетевых вызовов для этой правки не было; ускорение этим тестом не измерялось.

## Наблюдения ограниченных живых проверок

### Уточнение даты резолютивной части от 20.10.2026

По Telegram сообщениям пользователя 66 и 72 отдельная дата имеет приоритет.
При её отсутствии и наличии текущего раздела **РЕШИЛ** используется дата
текущего документа / решения. Один **ОПРЕДЕЛИЛ** или **ПОСТАНОВИЛ** для
подстановки не подходит. Прежние отдельные даты определений сохраняются;
невалидные/конфликтующие даты и чужие акты не обходятся подстановкой.

Кандидат хранит `basis=current_act_date_with_operative_section`, цитату даты,
позиции/цитату РЕШИЛ и зависит от подтверждения `decision_date`. JEV обязателен;
его отказ по дате решения снимает и зависимое подтверждение подставленной даты.
Общая конвенция расчёта окончания не меняется. Вопрос оператору №7 закрыт.

На 355 текстах кандидатов даты стало **345 вместо 174**, все прежние сохранены.
Непустых ручных дат этого поля только четыре: совпадают **4/4 вместо 1/4**.
Все 171 новые подстановки оператор относит к Решениям; 170 дат совпадают с
ручной датой решения, в p2885 исходник отличается от ручной правки.
Остались девять Определений и обрыв OCR p2125. Полных наборов 13 обязательных
кандидатов **261 вместо 128**, до JEV. Остальные 26 полей не изменились.
Проверены 1524 теста (без двух известных старых GLM-тестов), 1420 преобразований
и SHA-256 1420 файлов. Сети не было.
[Отчёт](../../analysis/pau-intro-decisions-2026-10-20/resolutive-act-date-policy-20261020/REPORT.md).

Первый полный прогон обнаружил лишние повторы при `early_report_required=false`:
отсутствие обязанности не имеет положительной цитаты, поэтому применяется прежний
контракт LLM с объяснением отрицательного ответа. Положительное поручение требует
подтверждающего фрагмента. Пробелы в цитате могут отличаться; программа находит
фрагмент в источнике и сохраняет точные исходные позиции и текст.

Для длинных частей акта адресный LLM fallback возвращает два коротких дословных
якоря `start_anchor` и `end_anchor`. Программа проверяет их однозначность и порядок
и вырезает неизменённый исходный текст. Это предотвращает переписывание больших
фрагментов и отказ модели из-за объёма. Дополнительно проверяется полнота:
начало сразу после начального маркера, конец перед РЕШИЛ/ОПРЕДЕЛИЛ,
электронной подписью либо концом документа согласно полю. Пропуск конечных
абзацев вызывает адресный повтор, даже если оба якоря дословно найдены.
Результат считается полученным LLM;
повторного запроса к JEV нет.

ФИО должника в общем ответе сохраняет прежнюю структуру:
`debtor_last_name`, `debtor_first_name`, `debtor_patronymic`.

### Утверждённое правило даты из окончания процедуры

Telegram119 / update490870868: если явная дата следующего рассмотрения не
найдена, next_session_date заполняется датой окончания процедуры. Явная дата
имеет приоритет даже при отсутствии времени; отсутствующее время остаётся null.
Кандидат сохраняет selection_basis=explicit_appointment либо
procedure_end_fallback. При подстановке JEV проверяет именно дату окончания,
при явном назначении — назначение. Для next_session_date в документе выбирается
один вариант вопроса. Подстановка зависит от подтверждения procedure_end_date.
Отказ направляет только неподтверждённые поля в LLM с тем же приоритетом;
результат LLM повторно JEV не проверяется. Время и место не выводятся из
подставленной даты окончания. ФИО должника использует свой текущий режим,
описанный выше.

LLM возвращает обязательный discriminator `selection_basis` для этой даты;
отсутствие/некорректность маркера вызывает адресный повтор. Уже подтверждённое
JEV окончание передаётся LLM как reference, чтобы подстановка сохраняла ту же
дату. После merge проверяются соответствие итоговому окончанию и отсутствие
необоснованных времени/адреса при подстановке. Вопрос оператору8 закрыт.

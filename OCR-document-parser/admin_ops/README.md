# Админ-бот OCR: Пульс и Наладчик

Это отдельный контур для production VPS. `admin-bot`, `awg-gateway`, `pulse-ai` и `fixer-ai` включены в обычный `docker compose up -d` через `include` в основном Compose-файле (Docker Compose 2.20+). Основной OCR API и worker не получают Codex SDK и Telegram-токен. Любая AI-роль работает через Python Codex SDK с входом ChatGPT, а не через Responses API или Platform API key. Лимиты подписки Codex всё равно действуют. Без обязательных `OPS_*` переменных, нового VPN-профиля и авторизации Codex первый запуск не состоится.

`awg-gateway` использует официальные исходники AmneziaWG Go и `awg-tools`, зафиксированные по commit SHA. Два AI-контейнера и `telegram-proxy` разделяют его сетевое пространство; OCR API, worker, PostgreSQL, Prometheus и `admin-bot` остаются в обычной Docker-сети. Pulse слушает `8080`, Fixer — `8081`, Telegram-прокси — `8888`; эти порты не публикуются на VPS. Firewall шлюза разрешает через обычный Docker-интерфейс только UDP к VPN endpoint и ответы на входящие запросы к этим трём портам. При падении туннеля исходящие запросы не переключаются на сеть VPS. DNS работников и прокси задан отдельным `resolv.conf`; встроенный Docker DNS `127.0.0.11` блокируется до NAT. Не менять это на `network_mode: host` и не запускать полный туннель на самом VPS.

Для `getUpdates` и `sendMessage` бот использует отдельный HTTPX-клиент с `OPS_TELEGRAM_PROXY_URL=http://awg-gateway:8888` (уже задан в Compose, новых секретов не нужно). Tinyproxy разрешает только домен `api.telegram.org` и CONNECT на порт 443, не расшифровывает TLS и не получает токен. База, Prometheus, GitHub и AI HTTP endpoints не используют этот прокси. Обход прокси при ошибке отсутствует; при недоступности VPN сообщения Telegram и уведомления недоступны до восстановления связи. Проверка `healthy` у прокси подтверждает локальную готовность и фильтр, но не доступность Telegram. HTTPX/httpcore request/debug логи бота выключены, чтобы URL с токеном не попадал в журнал.

При обновлении gateway пересоздавайте также все три контейнера, разделяющие его network namespace. Сначала соберите образы, затем остановите только `admin-bot pulse-ai fixer-ai telegram-proxy`, пересоздайте `awg-gateway` с `--wait` и поднимите эти четыре сервиса с `--no-deps --force-recreate`. OCR и базу останавливать не требуется. Существующая авторизация Codex остаётся в host-каталогах.

Контейнер `admin-bot` хранит Telegram-токен, читает агрегаты из PostgreSQL и фиксированные запросы к Prometheus. `pulse-ai` получает только агрегированный snapshot и не имеет доступа к БД, полному checkout исходников и документам. `fixer-ai` клонирует опубликованную ветку GitHub в `/work`, не монтируя локальный checkout, незакоммиченные файлы или документы. Codex работает в подпапке `OCR-document-parser` изолированного клона с `workspace_write`; независимая проверка допускает максимум 5 текстовых файлов в `src/ocr_platform/` или `tests/`, без удалений. GitHub-токен существует только в `admin-bot`; Наладчик не может отправить ветку или создать PR. Сейчас клонирование рассчитано на публичный репозиторий; если он станет приватным, понадобится отдельный безопасный доступ только на чтение.

Корень GitHub-репозитория — каталог `OCR`, проект находится внутри `OCR-document-parser`. Workflow должны лежать в `OCR/.github/workflows`. На VPS скрипт деплоя требует такой же структуры: `/opt/ocr-platform` — корень Git-клона, `/opt/ocr-platform/OCR-document-parser` — приложение с `docker-compose.yml`. Проверьте это до включения деплоя.

Два отдельных решения администратора: `/approve ID` создаёт черновик PR без изменения `main`; после просмотра PR и успешного CI команда `/confirm ID SHA8` проверяет точную ревизию PR, неизменность базы, список файлов и результат GitHub Actions, затем выполняет merge и запускает production workflow для полученного SHA. GitHub Actions выкладывает этот SHA по SSH и проверяет API `/health` и worker `/metrics`. Бот сообщает итог. Merge/deploy включён по умолчанию; бот не запустится без `OPS_GITHUB_TOKEN`. До проверки GitHub secrets, CI и VPS можно временно установить `OPS_ENABLE_RELEASE=false`. CI здесь — policy/lint и smoke-тесты, **не** полная проверка качества OCR: паспортные и другие профильные изменения всё равно требуют предметной оценки перед `/confirm`.

## Подготовка на VPS

1. Создайте отдельного пользователя PostgreSQL только с `SELECT` на `documents` и `pipeline_runs`. В `OPS_DATABASE_URL` укажите именно его, не учётные данные рабочего OCR API. Установите в переменных окружения VPS `OPS_TELEGRAM_TOKEN`, числовой `OPS_ADMIN_IDS` (через запятую), случайный `OPS_INTERNAL_TOKEN` длиной от 32 символов и `OPS_DATABASE_URL`. Не коммитьте их в Git.
2. Создайте каталоги **вне репозитория**, например `/var/lib/ocr-ops/state`, `/var/lib/ocr-ops/codex-pulse`, `/var/lib/ocr-ops/codex-fixer`, для состояния бота (`OPS_STATE_HOST_DIR`) и авторизации Codex (`OPS_PULSE_CODEX_HOME_HOST`, `OPS_FIXER_CODEX_HOME_HOST`). Задайте им владельца UID `10001` и права `0700`; укажите абсолютные пути. Auth-каталоги доступны только соответствующим AI-работникам, с правом записи для обновления ChatGPT-сессии. Включите device-code login в настройках аккаунта ChatGPT. Пример переменных — в `.env.ops.example`; добавляйте их к существующему `.env` на VPS, не заменяя рабочие OCR-настройки.
3. Перевыпустите ранее опубликованные приватный и preshared VPN-ключи у провайдера. Новый профиль AmneziaWG храните **вне Git**: например, создайте `/var/lib/ocr-ops/vpn` с владельцем `root:root` и правами `0700`, а `/var/lib/ocr-ops/vpn/awg0.conf` — `root:root`, `0600`. В `.env` укажите только `OPS_AWG_CONFIG_HOST=/var/lib/ocr-ops/vpn/awg0.conf`; ключи в `.env`, Git, CI secrets и чат не вставляйте. Профиль должен содержать один IPv4/DNS endpoint и `AllowedIPs = 0.0.0.0/0`; gateway отвергает `PreUp`/`PostUp`/`PreDown`/`PostDown`, `Table` и `SaveConfig`. Проверьте `/dev/net/tun` и, до авторизации Codex, запустите и проверьте шлюз:

   ```sh
   test -c /dev/net/tun
   docker compose config --quiet
   docker compose up -d --build awg-gateway
   docker compose ps awg-gateway
   docker compose exec -T awg-gateway /usr/local/bin/awg-healthcheck
   docker compose exec -T awg-gateway ip -4 route get 1.1.1.1
   ```

   Маршрут должен указывать `dev awg0`; `awg-gateway` должен стать `healthy`. Сравните `ip=` из `curl -4s https://1.1.1.1/cdn-cgi/trace` на хосте и `docker compose exec -T awg-gateway curl -4s https://1.1.1.1/cdn-cgi/trace`: адреса должны отличаться. Проверьте из отдельной SSH-сессии, что OCR API по-прежнему доступен. Для проверки отказа без VPN при **ещё не запущенных AI-работниках** выполните `docker compose exec -T awg-gateway awg-quick down /run/awg0.conf`, затем проверьте, что `curl --max-time 5 https://1.1.1.1/cdn-cgi/trace` из шлюза не проходит. После проверки пересоздайте шлюз: `docker compose up -d --force-recreate awg-gateway`. Если сетевой выход остался, не запускайте Codex и разбирайте firewall.
4. Убедитесь, что `docker compose run --rm pulse-ai cat /etc/resolv.conf` показывает `1.1.1.1` и `8.8.8.8`, а не `127.0.0.11`. Только после этого войдите под тем же пользователем контейнера в ChatGPT через SDK. Для второй команды сначала задайте `OPS_GITHUB_REPO=suer-tech/OCR_document_reader` и `OPS_FIXER_CODEX_HOME_HOST`:

   ```sh
   docker compose run --rm --build pulse-ai python -m admin_ops.login
   docker compose run --rm --build fixer-ai python -m admin_ops.login
   ```

5. После входа проверьте авторизацию и лимиты Codex на VPS, затем запустите первый контур:

   ```sh
   docker compose up -d --build admin-bot awg-gateway telegram-proxy pulse-ai fixer-ai
   docker compose ps admin-bot awg-gateway telegram-proxy pulse-ai fixer-ai
   ```

6. Наладчик включён по умолчанию, но `/fix` требует авторизованного `fixer-ai`. `OPS_GITHUB_REPO` по умолчанию — `suer-tech/OCR_document_reader`; Наладчик читает опубликованный GitHub `main`, а VPS checkout не монтируется в его контейнер. Если `main` ушёл вперёд после предложения, старое предложение не публикуется. Для публикации PR укажите `OPS_GITHUB_TOKEN` с правами Contents (write), Pull requests (write), Actions (write) и `OPS_GITHUB_BASE_BRANCH=main`. CI `validate` читается отдельно без токена из публичного GitHub API; если репозиторий станет приватным, такой запрос должен завершаться отказом и понадобится новый способ авторизации. Используйте отдельный fine-grained token только для этого репозитория, не PAT с доступом ко всем проектам. Для временного отключения `/fix` задайте `OPS_ENABLE_FIXER=false`.
7. Добавьте workflow файлы из **корня репозитория** `OCR/.github/workflows/` в `main` и убедитесь, что `OCR Ops CI / validate` действительно запускается на ветке `codex/ops-*`. Защитите `main` правилом «только через PR» и обязательной проверкой `validate`; если возможен merge queue, текущий прямой merge нужно заменить на постановку в очередь. Настройте GitHub environment `production` и secrets `VPS_HOST`, `VPS_SSH_USER`, `VPS_SSH_KEY`, `VPS_SSH_KNOWN_HOSTS`. Для SSH используйте отдельного deploy-пользователя VPS, которому доступны только checkout `/opt/ocr-platform/OCR-document-parser` и необходимые команды Docker; не используйте root-ключ. Доступ к Docker фактически даёт высокие системные привилегии, поэтому выдавайте его только доверенному deploy-пользователю. Зафиксируйте реальный SSH host key в `VPS_SSH_KNOWN_HOSTS`, не выключайте проверку ключа сервера. Перед боевым включением проверьте чистый Git checkout в `/opt/ocr-platform`, ветку `main`, совпадение структуры каталогов и возможность `git fetch origin main` без интерактивного ввода пароля; затем проведите тестовую выкладку.
8. После настройки и проверки GitHub и VPS оставьте `OPS_ENABLE_RELEASE=true` (это значение по умолчанию) и пересоздайте `admin-bot`. Если workflow не существует, check не зелёный, PR изменился, ветка `main` ушла вперёд или VPS checkout содержит локальные правки, релиз останавливается. При потерянном ответе о merge `/status ID` сверяет PR с GitHub. Если бот получил тайм-аут при dispatch, он не повторяет запуск вслепую: ищет workflow run и через 15 минут переводит состояние в `deploy_unknown` для ручной сверки с GitHub Actions. `/deploy ID` допускается только когда merge подтверждён, а запуск ещё не предпринимался (например, процесс бота остановился между merge и dispatch).

## Команды

Обычный текст — постоянный режим диалога с Пульсом, без обязательного `/pulse`. На простое приветствие бот отвечает сразу, без AI; на вопрос сначала присылает подтверждение и показывает «печатает…», затем результат. Подготовка AI-ответа не блокирует получение следующих сообщений и быстрые команды. Для каждого администратора вопросы выполняются по порядку; максимум три незавершённых вопроса, включая текущий. При заполнении очереди бот просит отправить вопрос позже. Последние шесть успешных обменов хранятся отдельно для каждого администратора в памяти: история и незавершённые вопросы сбрасываются при перезапуске, их нужно отправить повторно. Сохранение диалогов на диск не включено.

Обычный текст никогда не запускает Наладчика, публикацию PR, merge или deploy. Для изменений нужна явная команда `/fix`, последующие подтверждения сохраняются. Неизвестная slash-команда возвращает подсказку, а не передаётся AI. Полный AI-ответ не гарантирован мгновенно: время зависит от получения метрик и Codex; на обработку одного вопроса установлен лимит 6 минут. Telegram и VPN должны быть доступны для подтверждений и ответов.

- `/today`: завершённые сегодня запуски по типам документов, ошибки, ретраи и средняя длительность. Время дня — `OPS_TIMEZONE` (`Asia/Yekaterinburg` по умолчанию); времена БД трактуются как UTC.
- `/health`: доступность API/worker exporters, запросы в секунду, HTTP 5xx, p95 и очередь RabbitMQ. `нет данных` означает, что конкретный ряд отсутствует или Prometheus не ответил; это не ноль.
- `/pulse вопрос` или обычный текст: диалог с Пульсом по обезличенному снимку данных.
- `/fix задача`: изменение в изолированной Git-копии, без PR и деплоя.
- `/diff ID`: полный diff частями в Telegram; `/approve ID`: создаёт черновик PR.
- `/confirm ID SHA8`: второе подтверждение, проверка PR и CI, merge и запуск деплоя. SHA8 выдаётся ботом после создания PR; команда с устаревшей ревизией не сработает.
- `/status ID`: состояние PR/merge/deploy; `/deploy ID`: запуск деплоя **только** если merge уже состоялся, но dispatch ещё не предпринимался.

Бот также раз в минуту проверяет фиксированные условия: `up == 0` для API/worker, доля 5xx >10% при ненулевой нагрузке и RabbitMQ ready >500. Уведомление уходит после двух последовательных наблюдений, повторяется не чаще раза в 30 минут и **не требует Codex**. Это первоначальные технические пороги, которые нужно откалибровать по реальной нагрузке; они не заменяют отдельный Alertmanager.

Не отправляйте паспортные изображения, тексты документов и необработанные логи в запросы боту. При недоступности Codex команды `/today` и `/health` остаются обычными программными ответами.

Production workflow не делает автоматический откат после ошибки smoke-проверки: бот помечает деплой как неуспешный и сообщает администратору. Предыдущий Git SHA выводится в лог workflow для ручного восстановления. Автоматический rollback требует отдельной процедуры и проверки того, как откатывать данные и схему БД.

Авторизация и sandbox описаны в [официальной документации OpenAI по Codex SDK](https://learn.chatgpt.com/docs/codex-sdk) и [авторизации Codex](https://learn.chatgpt.com/docs/auth). Хранилище `auth.json` содержит токены: защищайте его как пароль.

**Ограничение изоляции:** sandbox `read_only`/`workspace_write` ограничивает запись, но не является гарантией, что агент не сможет прочитать файл авторизации Codex внутри своего контейнера. Доступ к SDK в production допускайте только для доверенных администраторов; перед запуском Наладчика отдельно проверьте политику доступа к credential store и сетевой egress на VPS. Запрет удаления и PR-gate защищают проект от нежелательных правок, но не заменяют полноценную границу секретов.
